# Tailscale upgrades: one host at a time

A Tailscale upgrade can cut the host off the network it is managed over, so oupdate upgrades it on one host at a time, in a fixed order, and keeps the previous version until the host has proved it can still reach its peers. Every host runs its own `oupdate host --apply`; the order is enforced by each host asking whether it is its turn.

## Config keys (`apply` object)

| key | default | meaning |
|---|---|---|
| `riskyKeepPrevious` | `["tailscale"]` | packages whose previous version is kept through an upgrade and rolled back when the verify fails. Every entry has a release check (`releaseChecks`); `tailscale` has a built-in one. `[]` turns the list off. A name is matched by its last segment (`homebrew/core/tailscale` is `tailscale`), and listing a package twice that way is an error |
| `tailscaleCanaryOrder` | the order set in `src/apply/tailscale-sweep.ts` | host names, first the canary. A host that is not in the list never upgrades Tailscale (an unknown host is refused) |
| `tailscaleSweepRead` | none | argv (absolute first entry); the target version is appended. Prints the other hosts' records (`<host> <version>`, see below). With none, only the first host of the order may upgrade |
| `tailscaleVerify` | the local verify | argv that replaces the local verify, for example one that runs the ping from a peer. Exit 0 pass, 1 fail, anything else could not run |

All four are validated when the config is loaded; a wrong type, a duplicate host or a relative path is an error that names the key. While `tailscale` is in `riskyKeepPrevious`, an own `releaseChecks` entry for it is refused (use `tailscaleVerify` to change what the check runs): an own check would skip the record the sweep depends on. To use an own check, take `tailscale` out of `riskyKeepPrevious`.

While `riskyKeepPrevious` is not empty, brew's install cleanup is off for every upgrade of the run (brew's periodic cleanup after any upgrade would remove the previous keg) and the run's own `brew cleanup` leaves the risky packages out, on every host, whether or not a check is pending; every other package is cleaned by name as before. That `brew cleanup <names>` replaces brew's global cleanup on those hosts (brew has no way to exclude a package), so brew's cleanup of the download cache for formulae no longer installed does not run there; clear it by hand (`brew cleanup --prune=all` on a host with no kept previous keg to protect, or delete the files under `$(brew --cache)`) when it grows. The check the config makes for tailscale counts tailscale (and the tailscale app, by either token) as a gated package: an upgrade that would pull tailscale in as a new dependency waits, on every host, because that install would skip the turn check. The dependency read is made on every host, tailscale or not; a read that fails holds only that package.

## The turn

Before a Tailscale upgrade the run reads the version brew would install and decides:

1. The host is not in `tailscaleCanaryOrder`: held, `host <name> is not in tailscaleCanaryOrder (refused)`.
2. The host is first in the order: it goes, no record needed.
3. Otherwise `tailscaleSweepRead` is run with the version appended. Each line it prints is `<host> <version>` (a verified host) or `<host> <version> failed`. A line counts only for the version asked, spelled exactly: a line for another version (a stale record) is ignored, a line with no version cannot authorize anything. The host goes only when every host before it in the order is verified and none of them failed. **The reader must validate each record it reads (host, version and status) and that it is current (read live, not cached) before it prints a line**: oupdate trusts what the reader prints, and this host's removal of an invalidated record only reaches the fleet through the reader.
4. Any other case holds Tailscale for this run with the reason in the log: no reader set (`waiting for <host>: tailscaleSweepRead not set`), a reader that fails, times out, prints too much or prints something that is not this format (`gave no answer`: a line that is not `<host> <version>` or `<host> <version> failed`), a host before it that is not verified yet (`waiting for <host>`), a failed host before it (`the sweep stopped at <host>: its verify failed`). A hold is never an error: the rest of the run goes on and the next scheduled run asks again.

A failure at a host after this one does not stop it.

Before anything is installed, a real run also asks the host: a daemon plist must exist (`sh.brew.tailscale`, `homebrew.mxcl.tailscale` or the vendor's `com.tailscale.tailscaled`), the daemon must be running, and `tailscale status --json` must report the version in use now. Every label's plist that exists counts, up to three (`sh.brew.tailscale`, `homebrew.mxcl.tailscale`, `com.tailscale.tailscaled`), one target per label as the owner restart picks it (the system daemon, else the user agent): the restart requires each of them, so a second or stale one that is not running holds the host before the install, not after it, and `tailscale status --json` (the binary of `TAILSCALE_BIN` when it is set to an absolute path, else a bare `tailscale` found on the run's PATH, the same as the verify uses) must exit 0. Otherwise tailscale is held (`nothing is installed`), with no record and no effect on the fleet. A dry run reports the turn only.

**A host that holds here holds the sweep: every host after it waits for it**, and the hold repeats every run until the cause is gone. The run result says so (`tailscale held at this host's turn: <why>`, the run flagged). The way out, on that host, any one of: restart the daemon so it runs the version in use (`sudo launchctl kickstart -k system/<label>`, or `launchctl kickstart -k gui/<uid>/<label>`); remove the stale plist file (then `launchctl bootout` it if it is loaded: unloading alone leaves the plist, and the next run's pre-check holds again) so only the real daemon is left; take the host out of the order (remove it from `tailscaleCanaryOrder` on every host, so the hosts after it stop waiting for it and it never upgrades Tailscale); or uninstall the brew formula when the host runs the vendor's app (`brew uninstall tailscale`).

The version is bound to the decision, and the comparison is **exact** (a revision `1.80.2_1` is not `1.80.2`). The turn is decided on the version brew offers; the pending record keeps that authorized version before the install starts. Right before `brew upgrade` the run reads the version again and holds (nothing installed, the next run decides again) when brew now offers another one. That read is the last before `brew upgrade`, which installs by name; the window that remains is the time between that read and the install. On every recovery (the same run, or a later one) the installed keg is read again and compared to the authorized version: another release is a confirmed fail, rolled back and held here, with no sweep record (that release was never tested, so there is nothing for the fleet to read). A pending record with no authorized version (written before it was kept) authorizes nothing and is treated the same way, a saved PASS included: a recovered PASS is published (and older kegs pruned) only when the record's authorized version is the version that passed and a fresh read of the installed keg is that version too; a host changed since the PASS (rolled back by hand) drops the PASS and publishes nothing. A keg that cannot be read keeps the check pending.

A real run takes this host's sweep lock (`<stateDir>/tailscale-sweep/lock`) before it reads any pending check and releases it in a `finally` at the end of the run, so two runs of one host never decide at once. A run that cannot take it (another run holds it, or the real error is logged when the lock file cannot be written) holds tailscale, runs no turn check, does not recover or write the pending tailscale record at all, turns brew's install cleanup off and keeps tailscale out of its own cleanup, and in its stale-keg step reports a tailscale process still on a deleted keg without restarting it (the run that holds the lock restarts or rolls back). The host's record of a version is removed when an attempt starts, right before the install.

Across hosts the reader decides, and only the records decide: there is no `started` line. oupdate orders hosts within one version and cannot revoke a decision a follower already made: a follower that read the records of a version while a host was redoing that version has already gone. So run the hosts one at a time and clear records as below when one is redone. Fleet-wide one-at-a-time is the reader's and the operator's job.

The tailscale cask (the GUI app, `tailscale` or `tailscale-app`) is never upgraded by the apply run while `tailscale` is risky, on any host: update the app by hand.

## The upgrade, the verify and the rollback

The upgrade is a release check (see `src/apply/release-checks.ts`): the previous keg is kept (install cleanup is off and the run's own cleanup skips tailscale, see above), `brew upgrade`, then the owner is restarted, then the verify runs with `GATE_VERSION=<installed version>`.

The owner restart is required: the daemon on the host is named by the plist it runs from (`sh.brew.tailscale`, `homebrew.mxcl.tailscale`, or the vendor's `com.tailscale.tailscaled`). A risky tailscale with no daemon to restart could not run (no verdict, the check stays pending). A daemon that is not running after its restart is a failed verify (below), never a pass. A vendor daemon that is not launched from the brew keg is a separate installation: the verify below compares the daemon's own version, which is what catches one left on another version.

The built-in verify (`src/apply/tailscale-verify.ts`) runs on the host being upgraded. It waits 10 s for a just-restarted daemon to settle, then looks up to three times (15 s apart) before a failure stands:

1. `tailscale status --json` (at most 20 s) must exit 0 and say `BackendState` is `Running`, `Self.Online` is true and the daemon `Version` is the installed version.
2. `tailscale ping --c 3 <peer>` (at most 30 s each) must answer from at least one of the next two hosts of the order (wrapping round). **A peer that is silent does not fail a healthy host when another answers; every peer silent while this host is online is a failed reach, and with a two-host order the sole peer decides.**

A command is stopped when it passes its limit: SIGTERM to its process group, then SIGKILL to the whole group after 2 s whether or not the leader has already gone. A command that hangs, exits nonzero, crashes (dies of a signal), floods its output, or a status that is not a JSON object, is a failed reach: exit 1, rollback. The verify answers 2, could not run, only when: the `tailscale` binary cannot be started (status or ping), there is no peer to ping (a one-host order), `GATE_VERSION` is not set, a verified record cannot be written, or an unexpected error inside the verify. A command whose standard output is longer than 8 MiB (stderr is ignored; counted in bytes over the whole output; a stream that fails part-way counts too) is cut, and a cut status or ping is a failed reach whatever its exit code (a custom `tailscaleVerify` that prints that much and exits 0 is a failed verify too). The most it can take with two peers is about 307 s (settle, three attempts of status and both pings to their limits plus the 2 s kill grace and the runner's last second for each, two waits), below the check's 600 s timeout; if that outer timeout ever fired it would still be no verdict.

A version is compared with the daemon's version by its release: a leading `v`, a `-t<hex>` daemon suffix, a `+build` suffix and brew's `_N` revision are ignored on both sides; any other suffix (`-rc1`) is another release. Because the `_N` revision is ignored there, a revision-only bump cannot show a daemon left on the old keg. (The authorization of what to install is exact, above.) The restored version's check (after a rollback) answers but writes and removes no record.

Exit 0 and 1 write the host's record, `<stateDir>/tailscale-sweep/<name>.json` (the name is the version with every character outside letters, digits and `.+-` written as `_` and two hex digits, so no two versions share a file): `{"host", "version", "status": "verified"|"failed", "at"}`, written whole under a name of its own then renamed. Exit 2 removes the record of that version, so an older one does not stand for a try that never decided. A saved verdict whose record is missing (the run died between the two writes) is written again on the next recovery, and again on every run until the write lands: a saved PASS is published before anything else is decided or pruned; a saved FAIL never waits on its record (the hold and the rollback run first, so a record that cannot be written never keeps a failed keg or its daemon in place), but the pending record is kept after the rollback, ended or not, until the failed record has landed. A record file that is there but names another host, version or status is written again. A record this host already published for a version whose PASS is later dropped or found unauthorized is removed first; the decision never waits on the removal: a marker on the pending record lists the versions whose file is still to go and asks again, every run, until each is gone, and while it is pending the run is flagged (`sweep record <path> still to be removed`) and no further upgrade of tailscale starts (`its sweep record of <version> is still to be removed`). A record that cannot be read (a directory at its path, no access) is written over once (an atomic replace heals one that is only unreadable) and flagged the same way when that fails too; it never holds back the hold or the rollback. A fresh attempt whose older record cannot be removed is held with nothing installed, flagged; its pending record stays, ended, with the version in the marker, so every later candidate is held (`its sweep record of <version> is still to be removed`) until the file is gone. The baseline of the tailscale check is the keg the opt link names: a version known only from `linked_keg` or the one installed keg is not taken for it, and the last read before the install holds it unless that keg is the one the rollback would return to. If the removal can never succeed (a directory at the path, no write access), clear the file by hand, then the marker clears itself. Until the file is gone the followers' reader may still read the old `verified` line: **the reader must also check that the record is the host's current one** (a pending or rolled-back version is not verified), and a host whose reader is not set holds its followers anyway; a PASS whose keg cannot be read now is not shown to the fleet meanwhile. The sweep records live under this host's own `stateDir`: what other hosts read is the reader's (`tailscaleSweepRead`) job, so a record this host removes is gone for them only as far as the reader reads it live. The release check reads the exit code:

- 0: the new version stays; the host is verified; the next host's reader sees it.
- 1: rollback. The new keg is uninstalled, the previous keg is relinked, the owner is restarted, the release is held (a newer one is tried), and the restored version is checked again. The record says `failed`, so every host after this one holds. An owner that cannot be restarted onto the new version (at the start or in the gate before the check) is a failed verify too, for tailscale only (other formulas keep "no verdict, the check waits"): the verdict is saved first, then the failed record is written (a record that cannot be written is logged and never turns the fail into no verdict), and the same rollback runs without the verifier having run.
- 2, or a timeout: no verdict. The new version stays, no record is written, and the hosts after it wait at this host. The check stays pending, so the previous keg stays protected from install cleanup and the next run of this host asks again (every run, with no limit) until it reaches a verdict.

After the relink, an opt link that is read and is missing, dangling, not on a keg of the Cellar or on another keg is a failed rollback (`ROLLBACK FAILED`, the by-hand recipe below, nothing restarted onto it; a rollback an earlier run recorded is checked the same way before the restart); only when the read itself failed (`brew --prefix`, `brew --cellar` or the link read did not answer) is it noted in the log and notified, and the restart and the check of the restored version go on. A rollback can itself fail (an uninstall, a relink, or the restart of the restored daemon): the host can then be left without a working tailscale. oupdate says so (`ROLLBACK FAILED`) and the operator recovers by hand: see the recipe below.

### Per daemon method

| how the daemon runs | upgrade and restart | rollback |
|---|---|---|
| a Homebrew service (label `sh.brew.<formula>`) | the owner restart of the release check (named by its plist, or the stale-keg restart) | relink the previous keg, restart the same way |
| a system LaunchDaemon owned by a vendor package | restart through `restartHelper` or `labelRestart` for its label | the same helper after the relink |
| a GUI app (a cask or a downloaded app) | not part of the order; update it by hand | reinstall the previous app |

## Clearing a stopped sweep

A `failed` record stops every later host for that version until the cause is fixed. After the fix, remove the failed host's record (the file for the version in `<stateDir>/tailscale-sweep/`) **and** the held release on that host (`<stateDir>/release-checks/holds/tailscale.json`, which keeps that host off the failed version) when that version should be tried again; or wait for a newer version, which has its own records. A host's failed record for an older version still blocks later hosts if the reader is offered that older version again.

### A stale record of a version that is not in use

Before each attempt the run lists `<stateDir>/tailscale-sweep/`. A `verified` record of a version newer than the one in use (the opt link's keg) that is not the candidate is stale: this host is not on that version (it was rolled back, by hand or by a run whose record removal failed). A record this host wrote (its `host` field is this host) is removed by the run and the attempt goes on. The attempt is held, nothing installed and flagged with the path, when the removal fails, when the record names another host (copied in, or from another machine's state: remove it by hand if it is not this host's), when a record file cannot be read, or when the directory exists but cannot be listed. A directory that is not there (a first run) holds nothing. Records of older versions, `failed` records and the version in use are never stale. The way out of a hold is to remove the file named in the flag (or fix the permissions of the directory). The record of the candidate itself is removed at the start of an attempt only when it names this host; one that names another host, names no host, is not a record or cannot be read holds the attempt the same way (the file is left, the flag names it and why). A keg is blamed for an interrupted install only when it is the authorized version (brew's links name it, or the rack lists it): any other keg kept by hand is never taken for it, but a keg kept by hand that is exactly the authorized version cannot be told from the install that died, and is treated as it. The formula of the built-in tailscale check, when its opt link is bad or unread after an upgrade, is neither relinked nor restarted by the run's generic steps (the relink would pick the newest keg, and a daemon restarted onto a bad link stays down if the rollback is then refused): the run is flagged and the release check's own rollback and restart decide. The residual: if brew's own link step failed and the opt link cannot be read at the same time, the prefix links stay missing until the check decides; relink by hand (the recipe below) if it stays pending. A rollback that finds the opt link unread uninstalls nothing and waits for the next run (if it still waits run after run, roll back by hand: the manual rollback below); one that finds it bad, or not naming the failed keg, is refused for good (`ROLLBACK FAILED`, the recipe below), whether or not a version was authorized. A removal of a record marked for removal reads the record again and deletes it only when it names this host. If tailscale was uninstalled by hand while a pending record was left, the flagged check has nothing to roll back: remove `<stateDir>/release-checks/pending/tailscale.json` (and the hold, if it should be tried again). Records are cleaned only at the start of an attempt (not by every run). A link that is read as missing or on no keg, with no keg to blame (none on the pending record, none named by brew, the authorized version not in the rack), keeps the check pending and flags every run; nothing is rolled back or guessed: use the manual rollback below. After rolling a host back by hand, remove its record of the version you rolled back from, so the followers' reader stops reading it; the run does it on its next attempt otherwise.

An installed version that was never the authorized one is held locally and leaves no record: only its hold file keeps the host off it.

### A check that stays pending, and the manual rollback

A check with no verdict (no daemon to restart, a tailscale that cannot be started, a keg that cannot be read, a lock that cannot be taken) stays pending and is asked again on every run, with no limit. To give one up by hand, on that host:

1. List the kegs (`ls $(brew --cellar tailscale)`). `brew link` links the newest keg left, not a named one: if a keg newer than the previous version is there besides the new one, move its directory out of the Cellar first (and note where; oupdate's own rollback refuses in that case and says so). Then `brew uninstall tailscale` (the new keg), then `brew link tailscale` (or `brew link --force tailscale` for a keg-only install), and check that `readlink $(brew --prefix)/opt/tailscale` names the previous version.
2. Restart the daemon (`sudo launchctl kickstart -k system/<label>` for a system daemon, or `launchctl kickstart -k gui/<uid>/<label>`) and check it: `tailscale status --json` must say `Running`, online, and the previous version; `tailscale ping --c 3 <peer>` must answer.
3. Remove `<stateDir>/release-checks/pending/tailscale.json` (and the hold and the sweep record of the version, if it should be retried).

A lock file that cannot be written (a read-only state dir) holds tailscale with only a log line saying so; a lock held by a live hung process holds it until that process ends.

The previous keg is kept for good, not only while a check is pending: after a passed verify the previous version stays installed (a rollback stays one command away) until the next verified upgrade replaces it with the then-previous one. On a pass the run removes every keg of the package other than the verified one and the one before it (only names that look like versions: digits and dots with an optional `_N`; only under the package's own directory directly in the real Cellar, resolved through links; never a symlink, and never the keg brew's links name when it is read again just before the removal), for every package of `riskyKeepPrevious`, and no cleanup ever names the package. The previous keg, the verified one, anything newer than the previous one (a keg kept by hand), an entry that is not version-shaped, and either keg brew's `opt` link or `linked_keg` names are never removed; with the opt link not read (an unreadable prefix or link) nothing is pruned (and the result says so: `older kegs not pruned (its opt link could not be read ...)`, flagged), and a hand-kept newer keg does not stop older ones being pruned. For every package with a release check, brew's view of the installed version counts a keg only when its directory exists and resolves (links followed) to `<real Cellar>/<package>/<version>`, the Cellar being the one `brew --cellar` reports (it is not always `<prefix>/Cellar`): the opt link (an absolute target is taken as it is, a relative one from the link's directory), `linked_keg` and a single installed version alike; a `brew --cellar` that cannot be read or is not absolute counts nothing as installed, so the check stays pending, and an unreadable `brew --prefix` loses the opt link only. A rolled-back or undecided check removes nothing. The rollback itself fails closed: a rack that cannot be read, an entry in it (the candidate included) that cannot be statted, a directory in it that cannot be ordered, a keg that ties the previous one in another spelling (`1.78_0` and `1.78.0`: counted as newer), or a keg newer than the previous one refuses it before anything is uninstalled. A run that lost the sweep lock protects the keg the same way.

The verify reads `TAILSCALE_BIN` (an absolute path) in production. Its wait and limit knobs (`TAILSCALE_VERIFY_SETTLE_MS`, `TAILSCALE_VERIFY_RETRY_MS`, `TAILSCALE_VERIFY_CMD_TIMEOUT_MS`) are read only when `TAILSCALE_VERIFY_TEST=1` is also set, which only tests do.
